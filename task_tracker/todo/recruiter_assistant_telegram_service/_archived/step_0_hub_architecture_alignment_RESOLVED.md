## Вопросы для агента 00_anna

### Q1. Может ли hub-роутер проксировать **все** сообщения от юзера в наш проект, не только команды (`/`)?

**Контекст:** наш бот — гибридная архитектура (state-машина в коде + агент Claude Sonnet 4.6 на подхвате). State-машина требует обработки **non-command** сообщений: текст вакансии после `/refind_vacancy`, "ок"/edited boolean после показа boolean, "топ-3" / "почему провалил X" после результатов прогона.

**Варианты ответа:**
- (a) Да, роутер проксирует всё → бот **не** делает свой polling, hub-роутер дёргает наш handler на каждое сообщение
- (b) Нет, роутер только команды → бот сам подключается к Telegram через `python-telegram-bot` polling, hub-роутер участвует только в управлении проектом (start/stop/validate), не в message-flow

### Q2. Может ли handler быть async с возвратом "ack" + последующей отправкой результата отдельно?

**Контекст:** наш cv→jobs пайплайн занимает до 3-4 минут (Apify LinkedIn Jobs Scraper медленный). Hub-контракт требует timeout 120 сек. Не влезаем.

**Что нам нужно:** handler сразу отвечает "запущено" (1 сек), пайплайн продолжает в фоне через `asyncio.create_task`, финальное сообщение отправляется в TG напрямую (через `send_message` API) когда готово.

**Варианты ответа:**
- (a) Да, handler возвращает ack за 1-2 сек, дальше идёт отдельный flow
- (b) Нет, handler должен полностью обработать запрос за timeout — тогда нам нужно поднять timeout до 300 сек, или раздробить пайплайн на под-команды

### Q3. Структура `core/` вместо `tools/` — ОК?

**Контекст:** контракт hub описывает структуру с `tools/`. У нас выбрано `core/` для бизнес-логики (boolean_generator, candidate_screener), потому что это не "tools" в смысле LLM tools, а самостоятельные пайплайны.

**Варианты:**
- (a) Поддержать `core/` напрямую (роутер не требует жёсткой структуры)
- (b) Сделать симлинк `tools → core` — для совместимости с роутером
- (c) Переименовать `core/` в `tools/` — если роутер ищет именно `tools/`

### Q4. Multi-user через расширение OWNERS до списка — ОК?

**Контекст:** контракт говорит "Single-user: только Renat (OWNER_ID=<TG_ID>)". У нас на v1 два TG-аккаунта Рената (основной + тестовый). На v2 — потенциально больше юзеров через whitelist.

**Что нам нужно:** hub-роутер пропускает сообщения от любого `telegram_user_id` из списка `OWNERS` (или `WHITELIST`). Дальше наш бот через `config/whitelist.json` решает что делать.

**Варианты ответа:**
- (a) Да, OWNERS становится списком — вписываем оба ID
- (b) Один OWNER_ID за раз — тогда нам нужно либо два инстанса бота (overkill), либо обходить hub для второго юзера

### Q5. Handler не `claude_sdk_session` (используем чистый Python + OpenAI для основного флоу) — ОК?

**Контекст:** наш основной flow использует **OpenAI** (gpt-4o) для boolean+screening. **Claude Agent SDK** дёргается только для агента-помощника (через OAuth Max-подписки, без ANTHROPIC_API_KEY).

**Варианты ответа:**
- (a) Handler `python_async` (или аналог) — выполняет наш Python entry point, который сам решает когда/как звать Claude
- (b) Handler обязан быть `claude_sdk_session` — тогда мы оборачиваем всю логику в тонкий агент-shim

### Q6. Whitelist на стороне hub vs на нашей стороне

**Контекст:** контракт упоминает "OWNER_ID". У нас планируется собственный `config/whitelist.json` с проверкой при каждом сообщении.

**Что нам нужно понять:** есть ли у hub свой whitelist пользователей, синкается ли он с нашим, или это две независимые проверки (двойная защита)?

**Варианты:**
- (a) Hub-whitelist единственный источник правды → наш `whitelist.json` дублирует его (или вообще не нужен)
- (b) Hub пускает кого попало, наш whitelist единственный гейт → нужно убедиться что hub не игнорирует не-OWNERS
- (c) Двойная защита: hub-whitelist + наш whitelist (наш более строгий или равный)
